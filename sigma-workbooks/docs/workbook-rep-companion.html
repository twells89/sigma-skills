How an agent builds & edits a workbook
through the filesystem

The workbook rep: element-level editing over Sigma's whole-spec API — no middleware, no new interface. The spec becomes a directory of small files; the agent uses the file tools it is already best at; and a render loop means it sees what it built before calling it done.

THE WORKBOOK REP

1 · The element is the unit of work

Sigma's spec API moves whole workbooks — every small edit drags the full document through an agent's context, and parallel work is a merge hazard. The rep explodes the spec into one file per element and reassembles it on push.

Nothing is a new format: every file is a verbatim slice of the spec, so existing spec documentation applies unchanged to a single element file. A 20-element workbook becomes twenty ~600-byte files; an edit touches exactly one. Add an element = add a file. Delete = delete it. Reorder = rename the numeric prefix.

The element-level abstraction lives in the file layout, not in a process — the agent's native Read / Edit / Glob / grep are the API.
<rep>/ workbook.yaml name, folderId, … pages/ 010-overview/ prefix = order _page.yaml page identity _layout.xml layout XML block 010-revenue-kpi.yaml one element each 020-sales-by-region.yaml renders/ agent-readable PNGs .sigma/ snapshot + manifest

2 · The loop

pull→ edit files→ status→ push→ verify→ render & look→ repeat…

push reassembles the files and writes through four gates:

  1. Drift check — if the server spec changed since pull (a UI edit), push aborts and shows exactly what would be overwritten. No silent clobbering, ever.
  2. Diff preview — the element-level change set it is about to apply.
  3. Validation — static formula/shape checks before any network write.
  4. Readback — re-GET after the PUT, refresh the snapshot, report anything the server normalized.

The API still receives a standard full-spec PUT — element semantics arrive on top of the existing endpoint, today, with no server changes. Reassembly is byte-exact: an untouched rep pushes back as a no-op.

$ wb-rep status my-dashboard/ page "Pulse": ~ element "Clones per day" [columns, yAxis, color] + element "Star events per month" $ wb-rep push my-dashboard/ # drift-check · diff · validate · readback $ wb-rep render my-dashboard/ --page Pulse rendered "Pulse" -> renders/pulse.png

3 · The render loop — the agent looks at its work

A spec that POSTs cleanly and compiles cleanly can still be wrong. render exports any page or element as a PNG; the agent reads the image and critiques it against the plan. The acceptance criterion is "the pixels look right" — not "the API returned 200."

Failure classes only this gate has caught in practice:

  • a style the API accepted and silently dropped — element rendered with no background
  • a formula error inside {{…}} text templating — invisible to both POST and SQL compile, rendered as an error string in the banner
  • a chart that was numerically correct and visually useless
  • KPI panels clipping against a gradient band at real viewport widths

Zoom reads keep context spend near zero — the whole spec never enters context:

summarize <id|dir>pages, element kinds, sources — one screen
ls pages/<page>/one page, as a file listing
Read <element>.yamlone element, full detail (~600 bytes)
capabilities --kind K [--field F]what's authorable — distilled live from the public OpenAPI

4 · Beyond the schema — the verified-behavior catalog

The OpenAPI says what shapes parse; it can't say what the platform does. The rep's companion reference keeps a catalog where every entry is live-verified against the API and marked ✓/✗ with the exact error and workaround — which idioms are UI-only, which fields render although undocumented, which writes are accepted-then-dropped. When a render exposes a new behavior, it lands in the catalog the same day, and every future build inherits it.

5 · What the structure buys

Parallel builds. Element files are independent — a plan fans out one sub-agent per element with zero merge conflicts. The orchestrator owns the plan, the id namespace, and the layout; one push lands everything atomically.

Create mode. A rep authored from scratch (or exploded from any existing spec) POSTs a new workbook through the same gates. Plan-as-file-tree: the directory is the design doc.

Git-native. A rep commits cleanly: PRs show changed: revenue-kpi.yaml, not a 2,000-line spec diff. The snapshot is the merge base — workbooks-as-code falls out for free.

No installation, no server. One dependency-free script (Ruby stdlib) plus the agent's own file tools.
